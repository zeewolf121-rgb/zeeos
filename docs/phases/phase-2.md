# Phase 2 plan: Wayland desktop + base theme in the live session

**Exit criterion:** on `main`, `boot-test.yml` is green on all four cells (x86_64/aarch64 × Secure Boot on/off). Each cell's serial log has:
- `ZEEOS_DESKTOP_READY`
- `ZEEOS_THEME_OK`
- `ZEEOS_DARK_READY`
- a `ZEEOS_MEM` idle-RAM line

Each cell uploads a **light and a dark screenshot** showing the ZeeOS colour scheme and wallpaper, with no Fedora logo.

`ZEEOS_THEME_OK` is printed by a guest-side check, and only if all of these hold:
- the effective Qt colour scheme is ZeeOS's
- the GTK3 theme and the portal `color-scheme` agree with it
- GTK4/libadwaita follows the portal colour scheme and accent (libadwaita loads no third-party themes, ADR-0005)
- `fedora-logos` is not installed

Visual pixel-diff baselines are **report-only** in this phase. They become gating in Phase 3, once the design language settles.

## Scope rules for this phase

- **Theme, not layout.** Ship reusable components (colour schemes, GTK settings, cursor/font config, wallpaper) applied through `/etc/xdg` defaults. Keep Plasma's default panel. Phase 3 adds the three look-and-feel packages (Windows / Mac / Hybrid, ADR-0005) that reference these components.
- **Use what Fedora KDE ships** (Breeze icons and cursor, Noto fonts, which also cover Arabic for Phase 3 RTL). Any other font or icon set needs a licence check (ADR-0006) and a `decision` issue.
- **Scope: art belongs to theme-designer (`/branding`).** desktop-shell writes configuration only. The placeholder wallpaper is generated by a script, not committed art. theme-designer's final palette and wallpaper (#10, Phase 6) replace it by pointing the config at `/branding` files. Codex art therefore stays off the critical path without crossing scopes.
- **No new image wiring.** Everything desktop-shell adds lives under `desktop/live/overlay/`, which `build-iso.sh` already copies into the image (#68). P2-1 and P2-2 can run in parallel.
- **Package pinning order.** If `build/arch/*/packages.lock` exists on `main` when P2-1 merges (that is, #80/#82 landed first, ADR-0008), P2-1 must include the refreshed locks. The orchestrator dispatches `pin-packages` on its branch (see Orchestrator tasks). If no locks exist yet, P2-1 merges as-is, and #80 then pins the new package set.

## Marker protocol (fixed here so P2-4 and P2-5 can run in parallel)

All markers go to the serial console, one per line, in this order:
```
ZEEOS_THEME_CHECK
ZEEOS_DESKTOP_READY
ZEEOS_MEM total_kb=<n> available_kb=<n> used_kb=<n>
ZEEOS_THEME_OK scheme=<name> gtk=<name> portal=<prefer-light|prefer-dark>
ZEEOS_DARK_READY
```
- `ZEEOS_THEME_CHECK` announces that the image has the P2-4 check. The same unit prints it **before** `ZEEOS_DESKTOP_READY`, so the harness has always seen it by the time the legacy success marker appears. The harness (P2-5) requires the later markers only after seeing it, so P2-5 can merge before P2-4 without breaking boot-test. Once P2-4 is on `main`, every cell must reach `ZEEOS_DARK_READY`.
- On a failed check, print `ZEEOS_THEME_FAIL <reason>` instead of `ZEEOS_THEME_OK`, and skip the dark switch.
- The harness screenshots after `ZEEOS_THEME_OK` (light) and after `ZEEOS_DARK_READY` (dark), each with the TCG settle delay (#84, 90 s).
- There's no channel from harness to guest, so the guest waits **150 s** after `ZEEOS_THEME_OK` before switching to dark. That's longer than the harness's light-screenshot delay (90 s under TCG, 0 under KVM/HVF). Configurable on the kernel command line as `zeeos.dark_delay=<s>`. If the harness delay changes, this must change with it.
